## Clinical-staff onboarding wizard proposal (not built)

Keep HR-first. Add **Onboard clinical staff** as an administrator-guided entry point to the existing owners, not a second employee/user system. The present HR screen already has linked account creation, so the improvement should join its steps rather than replace working functionality. `apps/api/src/modules/staff/staff.service.ts:566`.

1. **Identity lookup:** search existing Employee, User and Practitioner by explicit identifiers; show possible duplicates. Never auto-merge on name/phone.
2. **Employment:** select active Department, clinical Position for Doctor, employment type, joined date and permitted salary metadata. Capture only hospital-approved fields.
3. **Credentials:** show license/document requirements and expiry warning using Credential ownership. Hospital must define which credentials block which work; do not invent policy.
4. **Login and roles:** unique username, optional email, temporary password policy, explicit role selection, least-privilege summary and mandatory first change. Explain Position versus Role.
5. **Clinical profile:** for Doctor reuse employee-number Practitioner when unlinked; link User and home-department membership. For Nurse/Lab/Pharmacy use existing role ownership; do not create fictional clinical profile entities.
6. **Work readiness:** verify service/department routing. Appointments/rosters are their existing owners; do not create an unimplemented per-doctor schedule/fee engine.
7. **Review and commit:** show exactly which records will be created/linked. Prefer one server command using existing service validations and a callback transaction for new Employee + User + UserRole + Practitioner + memberships. Hash password before transaction; recheck eligibility/uniqueness under suitable concurrency control; preserve existing entities; roll back all newly created identities on failure. Record attributable audit/outbox effects in the same transaction. Repeated submission needs idempotency and a payload fingerprint. Files must be staged/cleaned separately if uploaded outside the transaction.
8. **Acceptance gate:** synthetic clean onboarding, existing employee/profile reuse, duplicate username, invalid clinical position, exited/suspended employee, concurrency/retry, audit rollback, first-login password change and reception-to-doctor queue verification. A partial failure must not leave an orphan login with clinical access.

Proposed error: **“To create a Doctor, open HR → Employees, select or create the employee, choose a Clinical position, then choose Doctor under Create linked account. Ask an Administrator if HR is unavailable.”** This wording and wizard are proposals only.

## Permission checks and inert controls: what was actually established

- All 319 detected HTTP handlers are public or declare a method/class permission. This is a metadata coverage result, **not proof of correct authorization for every payload/conditional rule**. Global guards default deny. `apps/api/src/auth/auth.module.ts:1`; [_inventory.md](_inventory.md).
- patient.delete has no grants intentionally. No other empty grant row was found in the executable matrix. Roles in ROLES and NAV_ITEMS are cross-checked in the documentation validation report.
- A control with no direct onClick may submit a form, use a child Link, delegate a prop, or update state. It is **not classified as broken** on that evidence alone. Every unresolved trace is marked in [_audit/ui-actions.md](_audit/ui-actions.md); no “all buttons work” claim is made.
- The practitioner deactivate confirmation gap above is confirmed by inspected handler structure. Other destructive confirmations and frontend/API discrepancies require case-by-case review of the marked rows.
- Attributable financial/clinical mutation logging is supported through auditedClient; reads/auth logging is best effort, so “every action is guaranteed audited” is false. `apps/api/src/prisma/transactional-audit.ts:1`; `apps/api/src/prisma/prisma.service.ts:1`.
